对于 ERP 的 RBAC 权限工单，最合适的理解是：

> **预先描述图负责“案件必须怎样被安全地处理”；运行时生成图负责“这个具体案件到底要查什么”。**

不是把所有权限问题预先画成一张巨大的状态机，也不是把整个工单完全交给 Agent 自主处理，而是设计成：

```text
固定的案件生命周期
        +
动态生成的诊断子图
        +
严格受控的变更流程
```

可以概括为：**硬骨架、软调查、硬执行。**

---

# 一、先区分这个系统里的三张图

## 1. 授权关系图

这是 ERP 权限本身的逻辑关系：

```text
用户
 ↓
用户组 / 岗位 / 组织
 ↓
角色
 ↓
权限
 ↓
业务动作
 ↓
资源范围
 ↓
条件、拒绝规则、职责分离规则
```

例如用户无法审批采购单，真正的授权链可能是：

```text
张三
 → 华东采购组
 → 采购主管角色
 → purchase_order.approve
 → 仅限上海组织
 → 金额上限 100,000 元
 → 当前采购单属于杭州组织
```

表面上是“用户有采购主管角色，为什么还不能审批”，实际失败原因可能是：

* 角色没有生效
* 组织范围不匹配
* 金额超过审批上限
* 工作流状态不允许审批
* 存在显式拒绝规则
* 用户会话中的权限缓存没有刷新
* 临时授权已过期
* 职责分离规则阻止操作
* 资源属于另一个租户
* 后端授权与前端菜单权限不一致
* 系统最近变更引入了缺陷

所以，即使系统叫 RBAC，真实 ERP 往往是：

```text
RBAC
+ 组织范围
+ 数据权限
+ 条件权限
+ 工作流状态
+ 职责分离
+ 临时授权
+ 显式拒绝
```

Agent 的目标不是只查询“用户拥有哪些角色”，而是重建一次完整的 **effective permission decision**，即系统为什么最终允许或拒绝。

---

## 2. 诊断依赖图

这是为了解决当前工单，需要收集哪些证据。

例如：

```text
用户身份 ───────────────┐
角色和用户组 ───────────┤
权限定义 ───────────────┤
组织与数据范围 ─────────┤
资源当前状态 ───────────┼→ 权限决策重放 → 根因判断
工作流配置 ─────────────┤
显式拒绝规则 ───────────┤
会话与缓存 ─────────────┤
近期变更与审计日志 ─────┘
```

这张图通常不是完全固定的。

每个工单需要调查的方向不同，因此可以由 Agent 根据工单内容动态展开。

---

## 3. 工单处理控制图

这是整个客服案件必须遵守的生命周期：

```text
接收工单
  ↓
识别用户、租户、资源和动作
  ↓
验证信息完整性
  ↓
判断风险
  ↓
收集证据
  ↓
诊断
  ↓
独立验证
  ↓
选择解决方式
  ├→ 给出使用说明
  ├→ 建议管理员修改配置
  ├→ 提交授权变更审批
  ├→ 识别产品缺陷并转研发
  └→ 无法确定，升级人工
  ↓
执行或回复
  ↓
验证结果
  ↓
记录审计信息并关闭
```

这张图不应该完全交给模型自由决定，因为其中包含：

* 安全边界
* 身份验证
* 审批要求
* 写操作权限
* 审计要求
* 升级机制
* 结束条件

它更适合预先描述。

---

# 二、推荐的总体架构

可以把系统设计为下面这样：

```text
┌──────────────── 固定宏观图 ────────────────┐
│                                            │
│ 工单接入                                   │
│    ↓                                       │
│ 实体识别与标准化                           │
│    ↓                                       │
│ 信息完整性检查                             │
│    ↓                                       │
│ 风险分类                                   │
│    ↓                                       │
│ 动态诊断节点 ──────────────┐               │
│    ↓                       │               │
│ 证据验证                   │               │
│    ↓                       │               │
│ 根因分类                   │               │
│    ↓                       │               │
│ 解决方案生成               │               │
│    ↓                       │               │
│ 安全与政策检查             │               │
│    ↓                       │               │
│ 人工审批 / 自动回复         │               │
│    ↓                       │               │
│ 执行与事后验证             │               │
│    ↓                       │               │
│ 关闭工单                   │               │
│                            │               │
└────────────────────────────┼───────────────┘
                             │
              ┌──────────────▼──────────────┐
              │ 运行时生成的诊断子图        │
              │                             │
              │ ┌→ 查用户和组织关系         │
              │ ├→ 查角色继承               │
              │ ├→ 查权限策略               │
              │ ├→ 查资源状态               │
              │ ├→ 查审批工作流             │
              │ ├→ 查拒绝规则               │
              │ ├→ 查缓存和会话             │
              │ └→ 查近期配置变更           │
              │            ↓                │
              │       汇总并形成假设         │
              │            ↓                │
              │    必要时继续生成调查节点    │
              └─────────────────────────────┘
```

这里的“动态诊断节点”本身可以是一个 Agent Loop。

也就是说，显式图中的一个节点内部，可以运行一个动态 Agent：

```text
宏观节点：diagnose_permission_issue
                ↓
内部 Agent Loop：
观察工单
→ 提出假设
→ 选择工具
→ 查询证据
→ 启动 subagent
→ 比较结果
→ 修正假设
→ 输出结构化诊断
```

# 三、哪些内容必须预先描述？

关键判断是：

> 这件事是“业务和安全不变量”，还是“案件调查策略”？

业务和安全不变量应该预先描述。

## 1. 工单生命周期

例如必须经历：

```text
接收
→ 诊断
→ 验证
→ 解决
→ 事后检查
→ 审计关闭
```

模型不能因为“已经很有把握”而跳过审计或验证。

---

## 2. 身份和租户边界

Agent 调用任何工具前，都应该已经确定：

* 哪个租户
* 哪个环境
* 哪个用户
* 哪个业务资源
* 哪个操作
* 工单提交者是否有权查询该用户的信息

这些不应该由 subagent 自由猜测。

信息不足时，固定图应进入：

```text
request_more_information
```

而不是让 Agent 在整个 ERP 数据库里搜索“可能是这个用户”。

---

## 3. 必须收集的证据

可以规定最小证据集，例如：

```text
用户身份
角色和组关系
目标动作
目标资源
当前权限判定
关键策略版本
相关审计记录
```

动态 Agent 可以增加更多调查，但不能缺少这些基本证据。

---

## 4. 风险分类

例如：

```text
低风险：
- 菜单未显示
- 权限缓存未刷新
- 用户不了解操作路径
- 已有权限但进入了错误组织

中风险：
- 角色分配错误
- 数据范围配置异常
- 工作流配置错误

高风险：
- 管理员权限
- 财务审批权限
- 跨租户访问
- 批量导出
- 薪酬、人事或敏感数据
- 职责分离冲突
- 提升权限
```

风险级别决定后续路径。

```text
低风险 → Agent 可以自动回复或建议重新登录
中风险 → 生成修复建议，管理员确认
高风险 → 强制人工审批和安全复核
```

---

## 5. 写操作的硬门禁

诊断 Agent 最好默认只有只读工具：

```text
查询用户
查询角色
查询策略
模拟权限判断
查询日志
查询配置历史
```

不能直接拥有：

```text
授予角色
修改权限
删除拒绝规则
改变组织归属
修改审批额度
```

需要修改时，应先输出结构化变更计划：

```json
{
  "change_type": "assign_role",
  "target_user": "U-1024",
  "role": "purchase_approver",
  "scope": "org:shanghai",
  "reason": "工单 INC-23891",
  "risk": "high",
  "expected_effect": "允许审批上海组织内10万元以下采购单",
  "rollback": "移除新增角色绑定"
}
```

然后由固定流程完成：

```text
生成变更计划
→ 策略检查
→ 职责分离检查
→ 人工审批
→ 执行
→ 权限重放验证
→ 审计记录
```

Agent 不能自行绕过这些边。

---

## 6. 结束和升级条件

固定图应明确：

* 什么情况下可以自动关闭
* 什么情况下要求用户补充信息
* 什么情况下升级权限管理员
* 什么情况下升级研发
* 什么情况下升级安全团队
* 最多调查多少轮
* 最大工具调用次数
* 最大运行时长
* 置信度低于多少不得给出确定结论

否则动态 Agent 可能不断调查，也可能过早结束。

---

# 四、哪些内容适合运行时生成？

运行时生成图最适合处理**未知性**。

## 1. 根据工单内容生成调查假设

用户可能只写：

> 我以前可以审批，现在审批按钮没有了。

Agent 可以生成候选原因：

```text
H1：用户角色被移除
H2：用户切换了组织
H3：采购单状态不允许审批
H4：审批额度低于订单金额
H5：权限配置最近被修改
H6：前端缓存未刷新
H7：系统发布引入缺陷
```

这些假设不必全部预先写进状态机。

---

## 2. 动态决定启动哪些 subagent

例如主 Agent 判断该问题涉及财务采购审批，可以启动：

```text
identity_agent
- 检查用户、岗位、组织、用户组

policy_agent
- 检查角色、权限和拒绝规则

workflow_agent
- 检查采购审批流程和单据状态

audit_agent
- 检查近期角色、策略和配置变更

runtime_agent
- 检查会话、缓存、令牌和前后端判定
```

另一个工单如果是“看不到员工工资”，可能生成完全不同的子图：

```text
hr_data_scope_agent
payroll_policy_agent
tenant_boundary_agent
sensitive_data_audit_agent
```

---

## 3. 动态选择工具和查询方式

Agent 可以决定：

* 查询权限 API
* 查询数据库只读视图
* 读取配置文件
* 调用权限模拟器
* 查询审计日志
* 编写临时分析脚本
* 比较两个用户的有效权限
* 比较变更前后的策略快照

这里无需为每一种可能的查询预先画一个节点。

---

## 4. 动态生成后续调查分支

例如最初发现用户确实拥有角色：

```text
有角色
  ↓
继续检查角色是否包含目标权限
```

发现角色也包含目标权限：

```text
有权限
  ↓
继续检查资源范围和条件
```

发现范围也正确：

```text
范围正确
  ↓
继续检查工作流状态和显式拒绝
```

这是一张运行时展开的诊断图。

---

# 五、一个具体例子

假设工单是：

> 用户王敏不能审批采购订单 PO-8932，但同部门的李强可以。

## 固定图第一阶段：标准化案件

提取为：

```json
{
  "tenant_id": "T01",
  "reporter": "王敏",
  "affected_user": "王敏",
  "action": "purchase_order.approve",
  "resource_type": "purchase_order",
  "resource_id": "PO-8932",
  "expected": "允许审批",
  "actual": "审批按钮不可用",
  "comparison_user": "李强"
}
```

这部分可以由 LLM 抽取，但输出结构固定。

---

## 固定图第二阶段：风险分类

采购审批属于业务敏感权限，因此：

```text
risk = high
```

这意味着：

* 可以自动诊断
* 可以自动生成修复建议
* 不允许 Agent 自动提升权限
* 修改必须经人工审批

---

## 动态诊断子图

主 Agent 生成并行任务：

```text
                    ┌→ 王敏的用户、岗位和组织信息
                    ├→ 李强的用户、岗位和组织信息
                    ├→ 两人的角色和权限差异
PO-8932 权限调查 ───┼→ PO-8932 的组织、金额和状态
                    ├→ 审批工作流当前节点
                    ├→ 显式拒绝和职责分离规则
                    └→ 最近七天权限及配置变更
```

这些主要是只读查询，可以并行执行。

---

## 汇合后形成权限解释链

例如得到：

```text
王敏：
采购审批角色：有
审批动作权限：有
组织范围：上海
审批金额上限：100,000

PO-8932：
所属组织：上海
金额：180,000
状态：待部门负责人审批
要求审批额度：200,000

结论：
角色和组织范围正确，但王敏的审批额度不足。
```

Agent 不应该只输出：

> 王敏缺少权限。

而应输出完整的决策路径：

```text
用户身份匹配
→ 角色有效
→ 操作权限有效
→ 组织范围匹配
→ 工作流状态匹配
→ 金额条件不匹配
→ 拒绝审批
```

这是一份可解释的 permission trace。

---

## 固定验证节点

诊断完成后，另一个验证器检查：

* 是否查询了正确租户
* 用户身份是否唯一
* 是否存在显式拒绝规则
* 是否考虑职责分离
* 审批额度单位和币种是否正确
* 对比用户是否真的处于相同上下文
* 证据是否足以支撑结论

验证通过后，才能进入解决路径。

---

## 固定解决路径

系统可以给客服生成回复：

> 王敏目前拥有采购审批角色，但该角色在上海组织内的审批金额上限为 100,000 元。采购单 PO-8932 金额为 180,000 元，因此系统按配置拒绝审批。这不是角色缺失问题。可以由审批额度达到 200,000 元的审批人处理，或者由权限管理员评估是否调整王敏的审批额度。

如果用户要求提高额度，则进入另一条固定图：

```text
提出权限变更
→ 职责分离检查
→ 业务负责人审批
→ 权限管理员审批
→ 执行变更
→ 模拟授权
→ 实际验证
→ 审计关闭
```

# 六、异步和阻塞怎么设计？

在这个系统里，可以采用 **late join**：尽可能晚地等待。

## 可以异步并行的任务

通常是独立、只读的调查：

```text
查询用户角色
查询资源状态
查询工作流
查询审计日志
查询会话缓存
查询近期发布记录
```

主 Agent 启动这些任务后，还可以继续：

* 整理工单文本
* 构造候选假设
* 查找类似历史工单
* 准备证据模板

---

## 必须阻塞的位置

### 1. 实体标准化之后才能查询

没有确定租户、用户和资源之前，不应启动广泛调查。

```text
实体识别
→ barrier
→ 并行查询
```

### 2. 根因诊断前需要必要证据

```text
角色查询 ─────┐
策略查询 ─────┤
资源查询 ─────┼→ 根因诊断
工作流查询 ───┤
拒绝规则查询 ─┘
```

但不一定等待所有补充性任务。

可以把结果分为：

* 必要证据
* 补充证据

必要证据全部完成才能诊断；补充证据可以晚一些返回。

### 3. 高风险结论必须等待验证器

涉及跨租户、管理员、财务、薪酬等权限时：

```text
诊断
→ 独立验证
→ 才能给出正式解决方案
```

### 4. 任何写操作都必须等待审批

```text
变更方案
→ 审批
→ 执行
```

不能“先后台执行，之后再通知管理员”。

### 5. 工单关闭前必须等待事后验证

修改成功不代表问题解决，需要验证：

* 权限模拟结果
* 用户实际操作结果
* 是否产生意外扩权
* 是否影响其他角色或组织
* 是否可以回滚

---

# 七、不要让动态 Agent 直接拥有整张系统图的控制权

一个常见失败设计是：

```text
用户工单
  ↓
超级 Agent
  ├→ 自己决定查什么
  ├→ 自己决定是否需要审核
  ├→ 自己决定是否修改权限
  ├→ 自己决定修改什么
  └→ 自己决定工单是否完成
```

这个方案演示时很灵活，但生产上存在几个问题：

* 调查步骤不可预测
* 强制检查可能被跳过
* 写权限边界不清楚
* 难以恢复中断任务
* 难以判断结论依据
* 同样的工单可能产生不同处理过程
* 无法清楚证明没有越权
* 很难满足审计要求

更稳妥的是把 Agent 放进受限槽位：

```text
固定图
  ↓
[动态诊断槽位]
  ↓
固定验证
  ↓
固定决策门禁
  ↓
[受控执行槽位]
```

Agent 可以在槽位内部自由探索，但不能改变槽位外部的不变量。

---

# 八、节点合同应该如何设计？

一个诊断节点不要只返回自然语言，而要返回结构化结果。

例如：

```json
{
  "status": "diagnosed",
  "root_cause": {
    "category": "approval_limit_mismatch",
    "summary": "用户审批金额上限低于单据金额"
  },
  "permission_trace": [
    {
      "check": "role_assignment",
      "result": "passed",
      "evidence": "role_binding:R-218"
    },
    {
      "check": "organization_scope",
      "result": "passed",
      "evidence": "org_scope:SHANGHAI"
    },
    {
      "check": "approval_limit",
      "result": "failed",
      "expected": 180000,
      "actual_limit": 100000
    }
  ],
  "confidence": 0.96,
  "missing_evidence": [],
  "recommended_resolution": {
    "type": "route_to_higher_approver",
    "requires_permission_change": false
  }
}
```

这样后续节点不需要重新阅读一大段 Agent 对话。

它可以直接根据字段路由：

```text
requires_permission_change == false
    → 生成客服回复

requires_permission_change == true
    → 进入权限变更流程

confidence < threshold
    → 升级人工

missing_evidence 非空
    → 继续调查
```

# 九、可以采用“调查者—验证者”双 Agent

权限问题非常适合把生成和验证分开。

## 调查 Agent

目标：

* 提出假设
* 收集证据
* 重建权限判定
* 提出根因

## 验证 Agent

目标不是重新解决，而是反驳调查结果：

* 是否有遗漏的显式拒绝？
* 是否混淆了用户和代理用户？
* 是否在错误租户查询？
* 是否把菜单权限当成后端权限？
* 是否忽略了组织和时间条件？
* 是否有权限缓存或延迟生效？
* 对比用户是否真的具有相同上下文？
* 解决方案是否会产生过度授权？

流程是：

```text
调查 Agent
    ↓
结构化诊断
    ↓
验证 Agent
    ├→ 通过
    ├→ 要求补充证据
    └→ 驳回并提出反例
```

如果验证器要求补充证据，可以形成有限循环：

```text
调查
→ 验证
→ 补查
→ 再验证
```

但必须限制最大轮数，避免无限调查。

# 十、如何选择“预先描述”还是“运行时生成”？

可以用两个维度判断：

```text
             后果低                      后果高

未知性高    动态 Agent Loop             固定骨架 + 动态诊断
            例如知识搜索                 例如财务权限问题

未知性低    简单脚本或固定流程           严格显式工作流
            例如刷新缓存                 例如管理员角色授予
```

## 预先描述图适合

* 业务流程稳定
* 必须审计
* 涉及权限修改
* 涉及敏感数据
* 某些检查绝不能跳过
* 需要可靠恢复
* 需要明确 SLA
* 需要可预测成本
* 需要人工审批

## 运行时生成图适合

* 问题描述不完整
* 可能原因很多
* ERP 模块众多
* 不同客户配置差异大
* 需要探索日志、配置和代码
* 工具调用路径无法预先穷举
* 需要根据新证据不断调整假设

# 十一、一个实用的工程原则

不要尝试预先画出所有可能的权限问题。

那会变成一张无法维护的巨大状态机：

```text
菜单问题
角色问题
用户组问题
组织问题
数据范围问题
工作流问题
缓存问题
前端问题
后端问题
配置问题
产品缺陷
……
```

真正应该预先固定的是：

```text
案件生命周期
安全门禁
最小证据要求
审批流程
审计要求
失败和升级机制
```

而不是固定：

```text
每一个可能的调查步骤
每一次数据库查询
每一种工具调用顺序
每一个可能的根因
```

所以对 ERP 权限工单系统，我会把 Graph Engineering 定义为：

> **预先设计一张不可绕过的案件治理图，并允许 Agent 在指定节点中，根据具体工单动态生成诊断子图；子图输出结构化证据，再回到固定图中完成验证、审批、执行和审计。**

最简化的结构就是：

```text
固定入口
→ 动态调查
→ 固定验证
→ 固定风险门禁
→ 受控执行
→ 固定事后验证
→ 固定审计关闭
```

这通常比“全 LangGraph”或“全 Agent Loop”都更适合复杂 ERP 权限业务。
