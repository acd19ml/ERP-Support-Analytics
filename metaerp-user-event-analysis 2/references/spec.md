# MetaERP 用户事件工单三维度判定规范

> 本文件是分类判据的唯一事实源：classify.py 运行时将本文件全文拼入 system prompt，人工复核也以本文件为标准。修改判据只改本文件。
> 本规范面向逐条判定：每次只判定一条工单，依据工单的标题、问题描述、解决方案三个字段。

## 第〇章 判定流程与输出约定

### 0.1 判定顺序（严格按序执行，命中即停的规则见各步说明）

1. **判定专题**：先独立匹配 IT/外部类五个专题（外部/颗粒、IT运维/基础设施、IT开发/测试问题、IT缺陷/性能问题、IT需求），五者之间无先后顺序。命中任一 → 专题判定结束，且**不再判定 L1/L2/解决方案（三者输出 null）**。
2. 未命中 IT/外部类 → 归入业务类：判断是否为【权限专题】；不是则专题输出"其他业务"。
3. **业务类工单（权限专题与其他业务）继续判定 L1**（8 类之一）。
4. L1 为 2/3/8 类时判定 L2（其余 L1 的 L2 输出 null）。
5. 判定解决方案分类（S1–S7，含 S4a/S4b/S4c）。

### 0.2 输出词表（严格从以下枚举中选择，禁止自创或改写类名）

- 专题：`外部/颗粒` | `IT运维/基础设施` | `IT开发/测试问题` | `IT缺陷/性能问题` | `IT需求` | `权限专题` | `其他业务`
- L1：`1-找不到页面入口/功能` | `2-系统使用咨询` | `3-操作失败/操作不生效` | `4-业务数据异常/原因定位` | `5-帮助查询/确认数据` | `6-帮助维护配置/操作` | `7-查不到数据` | `8-系统逻辑/规则咨询` | null
- L2：`2a-操作步骤指导` | `2b-如何申请权限` | `3a-异常报错` | `3b-功能入口不可用` | `3c-选值选不到/选不了` | `8a-规则/逻辑咨询` | `8b-功能能力咨询` | `8c-字段/接口/数据模型咨询` | null
- 解决方案：`S1-申请功能权限（角色）` | `S2-申请数据权限（数据维度）` | `S3-操作指引` | `S4a-澄清业务规则` | `S4b-诊断数据异常` | `S4c-解释权限规则` | `S5-数据查询` | `S6-后台配置/修复` | `S7-人工介入` | null

### 0.3 边界标记（输出字段"边界"）

以下任一情况将"边界"置为 true（供人工定向复核）：

- 工单命中第四章任一速查场景（多类别易混淆场景）
- 问题描述为空或信息量不足，L1 主要依据解决方案字段反推
- 两个类别的判据同时部分成立，最终按优先级规则裁定
- 权限相关工单在 S1/S2 与 S4c 之间、或 L1 在 2b/3a/7 之间存在取舍

其余情况"边界"为 false。

### 0.4 通用判定原则

- **L1 只看现象不看原因**：按"用户遇到了什么"归类，不按"解决方案是什么"归类。同一原因（如缺权限）可对应不同 L1：查不到数据→7；操作报错提示无权限→3a；不知道该申请什么权限→2b。用户附带的原因猜测（"是不是权限不支持"）不改变现象归类。
- **不急于对号入座**：先通读标题+问题描述+解决方案，理解用户的问题表象，再归类；不因单个关键词匆忙定类。
- **问题描述信息不足时**：可参考解决方案字段推测用户的真实问题表象，此时"边界"置 true。
- **解决方案分类单选**：一个工单可能涉及多个解决动作，取解决问题的关键一步，从"用户需要什么"的角度判断。

## 第一章 专题判定

### 1.1 【外部/颗粒】

**定义**：外部颗粒方用户提交的工单，华为 IT 运维无法直接处理，需颗粒方独立处理。

**正向线索**：
- 标题含【】中括号扩起的颗粒标识前缀：颗粒类型（颗粒化、B颗粒、BS颗粒、BG颗粒、CS、启云方颗粒）、业务集团编号（231、241、239、906）、部署环境（HCS）、系统环境标识（107、151、SIT、UAT、PRO、N网、RPO、生产环境）
- 问题涉及二开扩展点、版本升级/回退、刷数脚本
- 解决方案含"颗粒问题""颗粒侧""已联系SE/产品/BA""扩展点""刷数脚本""已提PM单"
- 颗粒方业务以财经/供应领域居多；典型解决模式：颗粒侧独立处理、版本出包修复、提供扩展点/刷数脚本

**易错点**：标题不含颗粒标识、但解决方案提到"颗粒侧""颗粒问题"的，也归本类（如标题为普通业务咨询、解决方案明确提到"颗粒侧服务物料"）。

### 1.2 【IT运维/基础设施】

**定义**：IT 运维人员主动发起的例行巡检、告警处理、资源管理、容灾操作，并非业务用户求助。

**正向线索**："巡检""CPU内存较高""EKS命名空间""资源分配率""查看redis""绑定容灾""查看hana""集成调度""数据库巡检""下线/回收"；来源多为 Others/WeLink；解决方案多为"确认无影响""已正常调度""可回收资源""待下线"。

**子场景**：EKS/容器巡检（资源分配率0%、CPU内存过高）、数据库巡检（大事务、SQL优化）、HANA/调度、容灾绑定、资源回收、开发自建单/测试验证单。

**易错点**：巡检告警不是 L1-3 操作报错——巡检是运维主动发起，不是用户在使用中报错。

### 1.3 【IT开发/测试问题】

**定义**：发生在测试/UAT 环境的问题，或开发人员调试接口、咨询接口调用方式、环境配置。

**正向线索**："测试环境""A1环境""UAT环境""接口调不通""接口报错""怎么调用""能不能给个测试环境""huat/beta域名"。

**子场景**：测试环境接口调试（URL调不通、504、参数问题）、测试环境功能不可用（菜单配置缺失、数据未初始化）、开发咨询（接口调用方式、字段含义、环境申请）、API 调用咨询（订阅后调不通）。

**负向线索/易错点**：
- 测试环境中的报错归本类；**生产环境**同类报错归 L1-3
- 用户 URL 含 beta/huat 域名、但实际是生产环境业务咨询的，不归本类

### 1.4 【IT缺陷/性能问题】

**定义**：已确认为系统缺陷或性能问题，通常已有或需提 DTS 缺陷单。

**正向线索**："请求次数过多""查询超时""加载慢""已经提缺陷单""DTS编号""打印功能缺失"；子场景：系统限流/版本回退、查询性能超时（需优化SQL/加索引）、功能缺陷（权限判断错误、附件下载卡住）、下载导出数据不准确（已拉研发确认）。

**与 L1-3 的区分**：3 类是用户首次遇到报错、需定位原因；本类是**已确认**为缺陷/性能问题。关键判据：解决方案是否提到 DTS 编号、缺陷单、版本回退、经运维/研发确认为缺陷。

### 1.5 【IT需求】

**定义**：用户提出新功能需求或优化建议，而非报告问题。

**正向线索**："是否可以给个API接口""是否可以增加""能不能支持""希望优化"；典型场景：申请开放 API 接口、自动化下载数据、增加页面显示内容。

**与 8b 的区分**：8b 是问"现在能不能/是否支持"（确认既有能力）；本类是"希望增加/开放"（提出新能力诉求）。

### 1.6 【权限专题】（业务类）

**定义**：工单核心诉求围绕权限的申请、切换、逻辑咨询——用户**明确围绕"权限"本身**发起咨询或申请。

**正向线索**："申请XX权限""权限没有了""切换角色""权限看不到XX""权限怎么申请""为什么我没有XX权限"；英文词汇 "permission" "privilege" "rights" "no right" "cannot access"。判据：标题或问题描述含权限相关词汇，或解决方案的核心是指导申请角色/权限。

**子场景**：申请角色/功能权限、申请数据维度权限、切换角色、解释权限逻辑（权限自动生成、维度取交集、生效延迟）、权限过期续期、跨 BG 权限不互通。

**与 L1-7 的区分**：7 类是用户使用中遇到查不到数据、权限只是可能的原因且用户不一定意识到；本专题是用户明确围绕权限本身提问。二者不互斥——权限专题工单同样要判 L1（专题与 L1 是上下位关系），例如"我没有XX权限导致查不到数据"→ 专题=权限专题，L1=7。

**易错点**：英文权限工单容易漏判，含上述英文权限词汇的必须归入本专题。

**角色名称易混淆对照**（判定与复核时注意）：

| 容易混淆 | 正确区分 |
|----------|----------|
| General_Accountant vs General Accountant | 下划线版本和空格版本可能是不同角色 |
| AP Inquiry vs General Inquiry | AP Inquiry 仅特定部门可申请，General Inquiry 可通用查询 |
| EISDP_Monitor vs RTS CNBG Monitor | 分别对应 EBG 和 CNBG 的监控角色 |
| PR Requester vs PR提单人 | 取消 PR 需同时是提单人且有 PR Requester 权限 |
| Business Handler | 不需申请，系统自动激活 |

## 第二章 问题表象 L1/L2 判定（仅业务类工单）

### 2.1 【1-找不到页面入口/功能】

**定义**：用户知道要做什么，但找不到入口。

**典型措辞**："在哪查""入口在哪""哪个系统""在哪里可以看到""怎么找不到""哪个模块""哪个页面"。

**负向线索**：找到入口但不会用→2；找到入口但查不到数据→7。

### 2.2 【2-系统使用咨询】

**定义**：用户已进入系统但不了解操作步骤，需要指导"怎么做"。只需系统使用知识即可解答，不涉及业务数据异常定位。

**典型措辞**："怎么操作""如何取消""怎么修改""在哪重试""怎么触发""操作步骤是什么""需要申请什么权限""权限怎么申请"。

**L2 细分**：

| L2 | 典型场景 |
|----|---------|
| 2a-操作步骤指导 | 怎么取消/修改/创建/触发，在哪重试/在哪维护 |
| 2b-如何申请权限 | 需要申请什么权限/该申请哪个角色/权限怎么申请 |

**负向线索**：不理解业务规则/逻辑→8；查不到数据→7；帮忙查数据→5；帮忙定位数据异常原因→4。

**与 8 的边界**：用户同时涉及规则和操作时，按核心诉求判断——问"能不能/是否可以/规则是什么"→8；问"具体怎么操作/步骤是什么"→2。例："直线法收入怎么触发"：不知道触发**规则**→8；知道规则但不知道在哪点击→2。

### 2.3 【3-操作失败/操作不生效】

**定义**：用户在操作中遇到系统报错、功能入口不可用、或选值选不到。问题表象是**操作受阻**，而非咨询规则或询问操作方法。

**典型措辞**："报错""失败""提交不了""校验失败""按钮灰色""点不了""无法操作""提示无权限""选不了""下拉没有选项""搜不到选项""打不开""没办法打开""无法下载""无法导出"。

**"能看到但不能用"场景**：用户能看到界面元素（附件、按钮、链接），但交互动作无法完成（打不开、点不了、下载不了）。关键词"打不开""没办法打开"不如"报错"直接，容易误分——判定要点：想操作但操作不了→3；不是查不到数据（用户说"能看到"就不是 7），也不是咨询规则。

**L2 细分（按用户看到的现象）**：

| L2 | 典型现象 |
|----|---------|
| 3a-异常报错 | 提交报错、校验失败、提示无权限、接口超时——系统给了即时文字反馈 |
| 3b-功能入口不可用 | 按钮灰色、点不了——功能入口物理性不可操作，无文字反馈 |
| 3c-选值选不到/选不了 | 下拉无选项、搜索无结果、维度/组织选不上——值域受限 |

**3a vs 3b 优先级**：文字提示与视觉拦截并存时（按钮灰色+弹窗提示），以文字提示为准归 3a；纯视觉不可操作无文字反馈→3b。

**负向线索**：问"怎么操作/如何修改"→2；问"规则是什么/是否可以"→8；"查不到数据"→7；解决方案中的"失败/报错"只是解释规则时的举例→8。测试环境报错→专题【IT开发/测试问题】；已确认缺陷（有DTS编号）→专题【IT缺陷/性能问题】。

### 2.4 【4-业务数据异常/原因定位】

**定义**：用户发现数据与预期不符，或需要定位"为什么"数据是这样。通常需查业务数据、核对上下游系统、结合规则判断原因。

**典型措辞**："数据不对""为什么是0""金额不一致""属性不对""与预期不符""为什么没有触发""反冲原因""不一致""不匹配""帮忙看下怎么回事""触发失败帮忙看下原因"。

**与 8 的区分（关键判据）**：用户是否提供了**具体单据 ID**（订单/发票/合同 ID 等）并对该单据的数据提出疑问。提供了单据 ID 并质疑其数据→4（需基于业务数据本身分析）；问题与具体单据无关、问总体功能特性或规则→8。

**负向线索**：不理解规则但数据本身无异常→8；只是需要获取数据→5；查不到数据→7。

### 2.5 【5-帮助查询/确认数据】

**定义**：用户明确指定了要查询的数据项或要确认的状态，需要运维代查或代导出。

**典型措辞**："帮查下""帮导出下""查询XX""提供XX数据""确认是否""核实下""查看消息"。

**负向线索**："帮忙看下为什么/怎么回事/原因"→4（定位异常，不是要数据）；"帮忙看下怎么操作"→2；"查不到数据"→7。

### 2.6 【6-帮助维护配置/操作】

**定义**：需后台/特权操作，用户自己无法完成。解决方案是**运维实际执行了后台操作**（而非仅告知用户如何操作）。

**典型措辞**："重新推送""帮忙配置""修改快码""提权""维护处理""可见性维护""品类用途配置"。

**负向线索**：运维只是告知操作步骤→2；运维只是解释了原因→4 或 8。

### 2.7 【7-查不到数据】

**定义**：用户**已在页面上**进行了查询或查看动作，但看不到数据。隐含"已经在已有页面"。与权限强关联。不设 L2。

**典型措辞**："查不到""搜不到""只能看XX区""无法查询""没有数据"。

**常见原因**（仅供理解，不作为归类依据）：缺数据维度权限、权限选择不全、涉密组织、跨 BG（两套权限体系独立，跨 BG 查数据需额外申请对应角色）、权限过期。

**负向线索**：咨询"该申请什么权限"→2b（还没到查数据这一步）；发现数据不对→4；进入页面时就报错提示无权限→3a。

### 2.8 【8-系统逻辑/规则咨询】

**定义**：用户不理解业务规则或系统逻辑，纯咨询——不涉及数据异常、不涉及操作受阻。用户没有遇到"问题"，只是不了解规则。

**典型措辞**："逻辑是什么""规则是什么""是否可以XX""能不能XX""是什么意思""字段含义""流程规则""解析规则"。

**L2 细分**：

| L2 | 典型场景 |
|----|---------|
| 8a-规则/逻辑咨询 | 触发规则、解析规则、匹配逻辑、摊销规则、核算规则等业务规则 |
| 8b-功能能力咨询 | "是否可以""能不能""是否支持""可以批量吗"等能力确认 |
| 8c-字段/接口/数据模型咨询 | 字段含义、底表/湖表、接口参数、枚举值、数据对应关系 |

**负向线索**：不知道怎么操作→2；发现数据异常→4；查不到数据→7；操作报错→3；提出新功能诉求→专题【IT需求】。

## 第三章 解决方案分类（仅业务类工单）

从"用户需要什么"出发，关注解决问题的核心交付物，而非运维的动作过程。单选，取关键一步。

### 分类总表

| 编号 | 定义 | 判断标准 |
|------|------|---------|
| S1-申请功能权限（角色） | 用户需获得角色/功能权限 | 解决方案核心是用户需要获得功能/角色权限 |
| S2-申请数据权限（数据维度） | 用户需获得数据维度权限 | 核心是获得数据维度权限（组织、公司、地区、账套等） |
| S3-操作指引 | 用户需知道在哪操作、怎么操作 | 交付行动指引（入口+步骤+是否需申请权限） |
| S4a-澄清业务规则 | 用户需理解业务规则/系统逻辑/功能特性 | 交付业务/功能知识，无需查具体业务数据，不涉及权限 |
| S4b-诊断数据异常 | 用户需基于具体业务数据理解异常原因 | 需查具体单据数据后分析解释 |
| S4c-解释权限规则 | 用户需理解权限逻辑 | 交付权限知识（角色对应、维度取交集、切角色、澄清后不需申请等） |
| S5-数据查询 | 用户需获得业务数据本身 | 交付数据/查询结果 |
| S6-后台配置/修复 | 需运维在后台执行操作 | 运维实际执行了操作（非仅告知） |
| S7-人工介入 | 超出当前系统能力，需人工协调 | 拉群/转交产品/提DTS/联系BA |

### 各类要点与边界

**S1**：典型："申请PO Query权限""去OnePro申请制造库存公共查询角色""需要WOM变更任务令_计划员权限"。与 S2 区分：S1 是功能/角色权限，S2 是数据维度权限。

**S2**：典型："补申请1581账套的查询权限""申请HW_CC库存组织的数据权限""需要申请涉密组织查询权限"。

**S3**：典型："在这个异常界面重试""先维护编码货位关系再重推""刷新页面再次导出""去收入触发工作台页面点击审批"。
- 与 S1/S2 边界：用户需**获得权限**才能解决→S1/S2（不管运维是告知还是帮操作）；用户已有权限、只是不知道怎么操作→S3
- 与 S4a 边界：规则理解是前提、操作是结论时，按最终用户需要什么判断——需要行动→S3；只需理解→S4a
- 与 S6 边界：运维**告诉用户**去操作→S3；运维**在后台执行**了操作→S6

**S4a**：典型："RAS 6月进行的金额拆分，所以匹配时间在6月""软件发布交付配置后会直接匹配金额""WOM代码里没有硬删这个表的情况"。
- 与 S4b 区分：S4a 不查具体单据数据，纯规则/功能说明；S4b 需结合具体单据数据解释异常
- 与 S4c 区分：S4a 解释业务规则（触发/匹配/核算逻辑）；S4c 解释权限规则（角色对应、维度规则、权限生效机制）

**S4b**：典型："看了001 PU没有金额，003的虽发货但只发软件，台套未齐套所以没有发货金额""此箱单还没入库，操作入库后会回写到ERP形成库存"。
- 与 S5 边界：用户要"理解为什么"→S4b（查数据是手段，交付分析解释）；用户要"得到数据本身"→S5

**S4c**：典型："公司和地代办都是权限维度值，会根据申请的权限维度值取交集""Business Handler不需申请，系统自动激活""当前权限已过期需续期""切角色即可解决""澄清后发现该角色已有，无需重新申请"。
- 与 S1/S2 区分（关键判据）：解决方案最终**是否让用户去申请了新权限**——是→S1/S2；否（只需理解逻辑，或澄清后不需申请）→S4c
- 与 S3 区分：S3 告知操作步骤（去XX页面申请XX权限）；S4c 解释权限逻辑（维度取交集、角色自动激活、过期机制）

**S5**：典型："通过SQL查询并导出销售员ID反馈给用户""反馈查询结果给用户""编码02354QVJ在BR2组织中"。

**S6**：典型："重新集成了调整单""已重新推送PR""品类用途已经配置完成""修改快码补充复核人员"。与 S7 区分：S6 运维有权限有能力直接解决；S7 运维也搞不定、需转交/协调。

**S7**：典型："已联系SE确认扩展点逻辑""拉群沟通，联系产品侧开发""已提DTS缺陷单""联系文控处理"。

## 第四章 跨类别易混淆速查（命中任一场景 → 输出"边界"=true）

### 场景1："帮忙看下"

"帮忙看下"本身不足以判 L1，看用户看的是什么：
- "帮忙看下为什么没触发/怎么回事/原因"→**4**（定位异常原因）
- "帮忙看下XX数据/帮查下XX"→**5**（获取数据）
- "帮忙看下怎么操作/在哪重试"→**2**（操作步骤指导）

### 场景2："无法XX"

- "无法提交/报错/提示XX"→**3a**（系统给了即时文字反馈）
- "无法点击/按钮灰色"→**3b**
- "无法查询/查不到数据"→**7**——但需进一步判断：进入页面时就报错无权限→3a；页面能用但输入条件后无结果→7
- "无法修改/无法操作"且用户在问"怎么修改"→**2**（问方法，不是报告失败）

### 场景3："申请权限"相关的 L1

- "我该申请什么权限/权限怎么申请"→**2b**（咨询申请步骤）
- "我查不到数据/看不到XX"→**7**（已在页面上但看不到数据）
- "我操作时提示无权限"→**3a**
- "帮忙配置权限/提权"→**6**（后台操作）

### 场景4："查询"相关的 L1

- "查询XX怎么做/在哪查/怎么查"→**2**（要方法）
- "帮忙查下XX数据/查询XX状态/进度"→**5**（要数据，运维代查）
- "查询不到XX/查不到"→**7**（遇到查不到）

### 场景5：解决方案字段中的"失败/报错"

- 用户问"规则/限制是什么"，解决方案解释规则时举例"超了会报错"→**8**（举例说明，非真实报错）
- 用户确实遇到报错但问题描述为空，解决方案还原了问题→**3**（还原真实问题）
- 无法确定时，优先按用户标题/问题描述中的直接表述判断

### 场景6："为什么"——4 还是 8？

- 用户提供了具体合同/订单/发票 ID 并质疑该单据数据→**4**
- 问题与具体单据无关，问总体规则/逻辑/特性→**8**

### 场景7："能看到但不能用"——3 还是 7？

- 能看到界面元素但交互动作无法完成（打不开、下载不了、导出不了）→**3**（有报错→3a，按钮灰色→3b）
- 页面上查不到数据→**7**（用户说"能看到"就不是 7）
- 用户附带原因猜测（"是权限不支持还是"）不影响 L1

**判断口诀：能看到→不是7；操作不了→3；问方法→2。**

### 场景8（解决方案维度）："需要申请XX权限"——S1/S2、S3 还是 S4c？

- 用户需要获得权限才能解决→**S1/S2**
- 用户已有权限、只是不知道在哪申请/怎么申请→**S3**
- 用户需要理解权限逻辑，或澄清后发现不需申请新权限→**S4c**

### 场景9（解决方案维度）：运维查了数据——S4b 还是 S5？

- 查完做了分析/解释/判断→**S4b**
- 查完只把原始结果反馈给用户→**S5**

### 场景10（解决方案维度）："重试/重新触发"——S3 还是 S6？

- 运维告诉用户去操作（去XX页面重试）→**S3**
- 运维在后台执行了操作（重推、重新集成、后台触发）→**S6**
